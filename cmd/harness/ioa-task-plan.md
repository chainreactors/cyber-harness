# 真实模型任务：订单 API 越权回归审计与交接

状态：测试设计，尚未实现或执行。目标是验证真实模型在应用 Agent 循环内完成有可判定结果的协作任务，包括 fork、活动子会话通信、自动留痕和后来者接手。沿用现有 IOA ext、subagent、Inbox、公开协议与 harness，不增加产品层抽象。

## 用户交给主 Agent 的任务

> 审计给定订单服务的两个接口版本：普通用户只能读取自己的订单。请将接口发现和权限验证交给不同的子 Agent，通过 IOA 共享线索、请求证据与结论。确认哪个版本存在越权，哪个版本通过本次检查，并提出修复与回归检查建议。原执行者结束后，安排没有继承其上下文的复核者，从 IOA 历史恢复调查经过并提交最终报告。报告必须引用实际 HTTP 请求和 IOA 消息。

模型负责选择、构造和执行实际工具调用；驱动只提供目标、任务约束、预算，并独立验收。驱动不得代发协作消息、补齐证据或改写模型工具参数。

## 可独立判定的业务目标

使用本地 Go HTTP 服务实现真实的订单查询与鉴权逻辑。数据是一次性测试数据；两个版本分别执行“只验证登录”和“同时验证订单归属”的代码路径。版本名称随机，不使用 vulnerable/fixed 等提示答案的名字，缺陷分配也随种子变化。

- 每轮生成两个用户、各自的订单 ID、订单内容标记、测试凭据和两个版本的路径。
- 接口文档给出路径、参数及测试订单归属；初始提示不包含具体订单 ID、版本结论或订单内容标记。
- 两个版本读取自己的订单均为 200；读取他人订单时，一个返回他人数据，另一个拒绝访问。无凭据均为 401；另设不存在订单的负例，不能将其当作权限保护的证据。
- 每个请求产生服务端 request ID，保存实际路径、调用者、订单归属、状态码和响应摘要。报告中的 request ID 必须对应这些真实请求。
- 答案由测试程序根据本轮生成的数据和实际 HTTP 行为判断，模型看不到服务实现、正确答案文件或服务端审计日志。

这是受控的实际 HTTP 功能任务，不代表对生产服务的安全验收。测试目标可以生成，Provider 回答和 Agent 执行不能用固定回放替代。

## 执行与信息依赖

| 角色 | 初始输入 | 工作与输出 |
| --- | --- | --- |
| 主 Agent | 目标地址、审计规则、测试用户凭据、随机审计批次标识 | 加入 IOA 空间，创建 B，再 fork A；等待真实完成通知，安排交接 |
| A：接口分析，fork | 继承父上下文；新增任务只描述职责，不重复批次标识与审计规则 | 实际读取接口文档，向 B 的 Session 发送路径、订单样本和归属；收到 B 的验证证据后核对业务规则，保存建议 |
| B：权限验证，async | 目标地址、测试调用者凭据、职责；没有接口路径、订单 ID 或 A 的发现 | 从 peer Inbox 收到线索后执行自己的订单、他人的订单、无凭据及不存在订单的请求；向 A 回复带 request ID 的证据，引用 A 的线索消息；保存最终结果 |
| C：交接复核，全新上下文 | 只有工作空间、审计目标描述、报告格式 | 原执行者结束后读取 IOA；恢复范围、两个版本的结论和请求证据，引用发现、验证和返回记录，发布最终报告 |

A 在收到 B 的证据前不能完成任务；B 初次验证前不能通过 `ioa read` 获取 A 的线索，必须证明自动 peer Inbox 投递。A 的地址由 B 收到的源 Session 获取，B 的地址由主 Agent 的派发结果或自动 delegate 记录获取，均不得硬编码。

fork 验收单独核对：A 的模型请求确实含继承的随机批次标识和规则，而新的 subagent prompt 未复制它们；自动 delegate 记录应含实际派发任务及 fork 模式。不能把“记录派发输入”解释为“IOA 自动保存全部父会话历史”。A 必须主动把后来者需要的审计范围写入 IOA。

子任务目前在输出最终答案后结束。等待协作证据时仅使用现有循环和有预算的 `ioa space nodes` 调用；模型请求总额仍计入预算。提前结束、等待耗尽都判失败，不自动重派或增加持久 Agent、wait 工具等产品机制。该等待方式的成本单独记录。

## 后来者接手与两种后端

1. **内存 IOA**：A、B 的 sessionEnded 和 return 记录齐全后，由主 Agent 创建 C，使用 async 新上下文，禁止 fork 或在派发提示中附带调查结论。存储留在同一应用进程中。
2. **外部 IOA**：A、B 完成后，主 Agent 结束，关闭原应用进程；保留 IOA 服务，启动全新应用进程 C 加入同一空间。C 不获得原进程文件或会话历史。

外部版本由驱动启动新的接手者是测试环境编排；A、B 必须由真实主 Agent 调用 subagent 创建。内存版本不要求跨进程恢复，两种后端不混淆持久性承诺。

C 只读取 IOA，不访问业务目标或本地报告文件。其报告从公开协议最终输出采集，并由 C 自己保存到 IOA。这让历史是否足够支持接手成为可观察结果。

## 验收条件

同时满足下列条件才通过，不以模型自述完成为准，也不匹配固定自然语言答案。

1. **业务正确**：只报告存在越权的版本；明确另一个版本仅通过本次检查。两者均包含自己订单成功和他人订单尝试的证据；无凭据与不存在订单的负例不能替代归属检查。
2. **真实执行**：报告引用的 request ID 与服务端日志相符，越权响应包含本轮他人订单的随机内容标记；请求来源、路径、状态、响应摘要一致。
3. **实际协作**：A → B 的线索与 B → A 的验证结果均由对应 Session 工具调用发送；消息具有正确源 / 目标 Session 和引用。接收者的后续真实模型请求包含对应 peer Inbox 消息，且发生在依赖该证据的动作之前。
4. **自动留痕**：每次真实子任务派发对应 delegate，结束对应 return，并关联实际父 Session、派发 call ID 和结果；每个 return 引用自己的 delegate。检查关联与内容，不依赖总消息数恒定。
5. **独立接手**：C 在 A、B 结束后才启动；其初始上下文没有调查事实。最终报告引用实际存在的 IOA 消息，并与服务端证据一致。外部版本还必须证明原应用进程已退出且 C 使用新 Node。
6. **生命周期**：父 Agent 实际收到 A、B 的完成通知后才能宣告调查结束；进程退出与资源释放受测试期限约束。已结束子任务无需、也不能被用作继续通信的接收者。

最终报告采用简单 JSON：审计范围、两个版本的结论、测试用例、HTTP request IDs、IOA evidence message IDs、修复建议。机器判定结构与事实；建议至少说明服务端按认证主体校验订单归属，并保留正反例回归。不要将猜测的实现位置或“全系统安全”作为结论。

## 实现范围与执行顺序

- 新增一个测试文件承载本地订单服务、场景与事实断言，复用 `stdioClient`、workspace、IOA 读取、证据记录和真实 Provider 转发。
- 现有模型网关仅允许两名 async worker 和固定消息语法，需要扩展本场景的明确角色、预算与 HTTP 命令检查；不建设通用任务 DSL、通信代理或角色框架。
- fork 的历史包含父任务，现有 `requestAgentRole` 从首条 user 消息判断角色会误识别。按当前派发任务标记识别，并与实际 Session 工具事件交叉核对；不能只按历史中出现过的角色名识别。
- 角色信息隔离在测试驱动中落实：解析实际工具调用，限制业务请求到本轮本地目标；B 在接收线索前不读工作历史，C 只能读写 IOA，不允许通过共享文件或额外模型请求绕过。此约束是测试条件，不声称产品已具备角色权限隔离。
- 先用无模型 HTTP 测试验证目标服务和判分逻辑，再跑真实模型内存场景，最后跑外部服务与跨进程交接。每轮保存种子、脱敏模型请求、公开协议日志、HTTP 审计记录、IOA 历史及最终报告。
- 初始预算：每种后端最多 60 次真实模型请求、每次最多 2048 输出 tokens、60 次业务 HTTP 请求、任务阶段总计 6 分钟；启动与清理另设有界超时。同步调整现有网关与子进程期限，避免被旧的 150 秒 / 4 分钟限制提前终止。记录实际 token、等待调用数与耗时，不自动重跑到通过。

这项任务覆盖安装 IOA ext 后的真实协作。不装 IOA ext 时的 fork 单次执行、断线恢复及多节点广播仍使用各自的独立验收，不能由本场景推断通过。执行真实模型阶段仍需显式 `CYBER_HARNESS_LLM_*` 配置。
