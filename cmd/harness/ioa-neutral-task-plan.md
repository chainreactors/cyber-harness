# 中立长流程验收：多来源数据整理、经营报表与交接

状态：暂停。首次实现通过了数据生成和真实进程接线检查，模型执行约 38 秒后按用户要求中止，尚未交付业务结果。新增数据夹具已撤下并归档到该次运行目录；下一轮采用自然语言定义的 [五子棋任务](gomoku-task.md)，避免为场景扩建夹具。旧方案和失败记录保留。

## 真实任务

交给 Agent 的初始需求：

> 整理两个渠道的订单、商品目录和退款数据，交付一个可重复运行的月度经营报表程序。报表需包含每日及各品类的订单数、销售额、退款额和净额，并说明重复数据、无法关联的数据和采用的统计口径。请用子 Agent 分工，通过 IOA 保存关键发现、核对结果和待办。交付可运行程序、测试、CSV 报表和简短说明。过程中可能补充数据或更换负责人。

不考察渗透、权限、漏洞或安全扫描。工作全部发生在隔离目录，不调用外部业务服务，不发送真实用户信息。使用合成交易数据和真实文件、程序、测试执行结果，不由模型编造数据处理结果。

## 最小工作对象

用 Python 标准库处理 CSV/JSON，不额外引入数据库、Web 服务、第三方依赖或工作流框架。约一万条记录，金额以整数分计算。

输入包含：

- 两个渠道的订单 CSV：字段名和时间格式不同，业务主键为 `(channel, order_id)`，同一渠道有重复导出的记录。
- 商品目录：SKU 与品类映射，包含少量未知 SKU；未知项单列，不能静默丢弃。
- 退款 CSV：一个订单可有多笔部分退款，有重复退款记录和无法关联的退款。
- `brief.md`：统计月份、时区、去重规则、异常处理规则和可核算的小样例；要求本身不故意含糊。
- 一个能运行但未实现统计的 `report.py` 入口，以及少量正常输入样例。Agent 完成实际实现，并自行增加测试。

基础口径公开给 Agent，也用于独立验收：订单按业务时区归属日期；唯一订单计一次；同一退款 ID 去重；销售额按订单归属日统计，退款额按退款发生日统计；净额为销售额减退款额；异常记录单列并保留源行引用。重复主键内容冲突属于异常，不任意覆盖。

所有数值由固定种子的生成器确定，生成器和独立验收期望保存在任务目录外。公开样例足以解释规则；隐藏数据仅变更 ID、金额、顺序和边界组合，不增加未公开规则。

## 为什么需要协作

建议形成三类工作，具体名称和拆分由模型决定：

| 工作 | 产物 | 实际依赖 |
| --- | --- | --- |
| 数据分析 | 字段映射、重复与异常分类、边界样例 | 将实际源行及处理建议发给实现者 |
| 程序实现 | 可重复运行的报表程序 | 根据分析者发现修正实现，回复采用的口径或冲突 |
| 独立核对 | 独立计算的样例及汇总、失败案例 | 使用实际程序产物，与源数据交叉核对 |

初期至少两个子任务执行重叠，包含一个 fork 和一个 async。分析者与实现者须在运行期间通过 IOA 交换具体数据事实，例如两个渠道出现相同订单号，接收者据此补充按渠道区分的测试或调整聚合键。不能只交换固定字符串，也不能只在任务结束后补写“已经讨论”。

保持一个代码写入者。源文件和程序是共享工作产物；任务安排、发现、口径决策和纠正通过 IOA 传递。派发和返回使用已有 ext 自动记录，模型不重复伪造 lifecycle 消息。

## 三个阶段

1. **基础交付。** 模型分析输入、派发子任务、实现程序并生成第一版报表，执行测试及独立核对，将当前口径和未完成事项写入 IOA。驱动只在程序实际运行成功、基础数据验收通过且初始子任务已完成后进入下一阶段。
2. **变更与修订。** 提供此前尚未发布的晚到退款，以及一份带生效日期的商品品类修正表。追加要求：品类按订单发生时有效的分类计算；晚到退款必须纳入，仍按退款发生日归属月份。Agent 更新实现和测试，重新生成结果，并在 IOA 说明哪些旧结论和报表被取代。数据来源、规则和修订文件名都明确给出，不让模型猜需求。
3. **换人接续。** 原负责人完成修订后，把剩余独立验收留给接手者，保存引用前文的 IOA 交接说明并结束。关闭原 Session；外部 IOA 模式还正常退出原 Agent 进程。新负责人仅获得业务目标、目录和 IOA 空间，读取历史，派发新复核任务，完成剩余验证、修正发现的问题并交付最终产物。

阶段推进依据可观察结果，不按任意时刻插入提醒。基础交付不合格、子任务未完成或没有交接记录就报告失败，不由驱动替模型补业务步骤。当前场景不叠加网络断线、503 或强杀进程，优先定位通用协作能力。

## 交付物与核验

执行接口保持简单：`python report.py --input data --output output`。允许在工作目录内新增必要的 Python 模块与测试，不强制只有一个文件；不新增专用 Agent 工具或通信协议。

交付物包括：

- 实际程序及 `unittest` 回归测试。
- `daily.csv`、`categories.csv`、`exceptions.csv` 和带输入摘要、程序摘要的 `summary.json`。
- `report.md`：统计口径、最终数值、异常和局限、发生的需求变更、IOA 证据引用。

独立验收重新执行程序并核对输出，不信任报告里的“测试通过”：

| 维度 | 通过条件 |
| --- | --- |
| 计算正确 | 对公开数据和另一组同规则新数据，逐日、逐品类及总计均匹配独立期望；正常记录和异常记录可追溯 |
| 可重复执行 | 对相同输入重复运行结果相同，不累加上一次输出；改变输入行顺序不影响业务结果 |
| 变更一致性 | 晚到退款和分类生效日期影响对应输出；旧版本结论被明确修订，最终输入/程序摘要一致 |
| 真实协作 | 子任务确实运行重叠；fork 继承范围；peer 消息实际进入接收者模型输入；此后可定位相关测试、代码或核对动作 |
| 交接有效 | 新 Session 不继承旧对话，外部模式使用新进程/Node；通过 IOA 恢复新要求和剩余验证并完成交付 |
| 记录完整 | delegate/return 关联正确；重要修订和交接引用已有消息；所有失败尝试保留 |

“消息已保存”和“接收者看到消息”分别记录。消息后的动作是否真正利用了该事实，还需抽查源行、时间顺序、测试和代码变化，不能仅靠出现相同词语判为因果关系。

## 复用现有机制与测试边界

复用现有真实可执行进程、stdio Session、subagent、IOA memory/external、模型网关和日志采集。新增内容仅为该场景的数据生成、输入材料、阶段驱动和独立核验。IOA 继续是可插拔 ext；不增设 core 消息总线、任务数据库、可靠投递层或新的角色抽象。

保持应用实际提供的文件工具、bash 和 subagent；允许读取其公开的内置技能说明。网关只负责请求目标、预算和明确边界，不按预设业务步骤过滤工具，也不拒绝合理的批量读文件。输入材料只读，工作目录外的验收材料不可访问；文件快照校验不能被称作操作系统沙箱。

沿用总上限：60 分钟、200 次模型请求、120,000 输出 tokens（含推理）、最多三个并发子任务。单次 token 和等待上限按实际 Provider 能力对齐，记录截断和超时，不能把无最终输出的截断当作完成。预期时长由实际执行决定，不插入无效等待制造长流程。

先做外部 IOA 一轮完整验收，再用相同业务场景验证内存 IOA 的进程内换 Session。单轮成功只证明该场景可行；多个预先固定种子的复验才用于估计稳定性。不得重跑到绿后隐藏失败。

## 开跑前的必要检查

此前安全场景的失败揭示了与业务无关的问题，需要先处理：Windows shell 引号执行异常、模型输出截断被标记为 completed，以及测试网关与应用的工具/资源/超时配置不一致。
