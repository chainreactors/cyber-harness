# 长流程验收：多租户订单系统的审计、修复、回归与交接

状态：首版测试入口已实现于 `long_task_test.go`，真实业务环境和应用接线已通过，但多次真实模型尝试均未完成全流程。按用户要求，停止将安全审计作为主场景，后续采用 [中立数据报表任务](ioa-neutral-task-plan.md)。旧实现与 `.runlogs/harness/` 失败记录保留，不计为通过。保留 `ioa-task-plan.md` 作为短场景；不通过插入等待制造“长任务”。

首版实现将源码写入限制在独立的 `policy.go` 与新增回归测试，原始 HTTP/SQLite/异步导出实现保持不变，独立验收会用新数据重新构建候选策略。需求变化在调查阶段的真实请求证据齐全后发出，交接在修复阶段结束且最终独立验收尚未执行时发出。是否发生活动子任务取消取决于当时任务状态，不能只凭负责人退出宣称覆盖了取消恢复。

## 交给系统的业务任务

> 接手提供的多租户订单与导出服务，完成一次发布前安全审计。确认权限边界，修复可复现的问题，保持现有正常业务可用，提供可执行的回归测试和有证据的交付报告。通过子 Agent 分工处理，使用 IOA 保留任务、关键发现、决策、变更和未完成事项。过程中可能收到新要求，也可能由新的负责人接手。没有验证过的事项必须明确保留为未完成。

只规定目标、边界和交付物，模型自行拆解任务、选择检查顺序、讨论证据并实施修复。驱动不逐条告诉模型下一步调用哪个工具，也不代写计划、消息、补丁或报告。

## 工作对象

准备一个固定基线提交的小型、完整 Go 项目，在隔离工作目录运行，包含网关/身份、订单、异步导出三个模块，约 15–25 个业务接口。模块使用真实 HTTP、SQLite、会话验证和导出任务状态；可以由一个测试服务进程提供不同监听地址，无需为测试引入微服务部署平台。

交付给 Agent 的材料：源码、正常业务测试、启动说明、API 文档、两个租户的测试用户及本地目标地址。生成种子决定账号、资源 ID、响应内容和过期时间，初始提示不包含缺陷位置与答案。测试程序持有独立的验收用例，模型可以读业务源码，不能读或改验收程序。

基线业务覆盖登录、订单列表/详情、创建导出、轮询导出状态、下载、权限变更。导出必须经历真实的 queued → running → completed 状态，轮询应有上限且遵守服务端提示。

基线含两个可修复问题：订单详情缺少租户归属校验；导出下载没有完整验证调用者权限。对照项包括公开说明页、合法管理员访问、同租户正常访问、无效凭据和不存在资源。公开数据或正常管理能力不能被误报。

隐藏验收同时验证漏洞修复与业务可用性：不能通过全部返回 403、关闭导出、删除路由或写死本轮资源 ID 来通过。另生成新账号和新订单验证补丁泛化；报告结论必须与实际运行的源码修订和数据批次一致。

## 六个工作阶段

| 阶段 | Agent 完成的业务工作 | 可核验的阶段产物 |
| --- | --- | --- |
| 1. 接手与基线 | 理解源码与业务边界、启动服务、跑已有测试、建立范围与计划 | 基线修订、启动地址、正常流程结果、IOA 中的范围/计划 |
| 2. 并行调查 | 分工发现接口、检查源码和动态验证；交换需要对方确认的线索 | 真实 HTTP 请求、确认与排除的候选问题、对应 IOA 消息链 |
| 3. 证据复核 | 区分越权、合法访问、过期凭据与暂时不可用；独立复核高风险结论 | 可重复步骤、归属依据、正反例、经修正或保留的结论 |
| 4. 需求变化与修复 | 接收新增要求，更新受影响任务；修改实际代码、增加回归测试、启动修订后的服务 | 代码 diff、测试文件、构建/测试结果、新旧修订与要求关联 |
| 5. 中途交接 | 原负责人保存进展并退出；新负责人从 IOA 和工作产物恢复，接续未完成验证 | 阶段摘要、证据引用、已完成/待完成边界、新 Session 的恢复计划 |
| 6. 最终回归与交付 | 在当前修订上验证原问题、新要求和正常流程；整理剩余风险 | 可运行补丁、回归测试、最终报告、结果与证据索引 |

这些是验收边界，不是驱动代执行的工作流。阶段 2–4 可交错；不要求固定派发数量、固定消息总数或固定措辞。阶段 5 必须发生在最终回归完成前，接手者需要继续工作，不能只是重述已有报告。

## 有意义的协作

建议角色为协调者、接口/源码分析者、动态验证者、修复者和独立复核者。最多同时运行三个子任务；允许角色分阶段复用，但修复者不能作为自己补丁的唯一验收者。

- 至少一次 fork 用于继承复杂业务范围。检查真实模型输入，确认继承发生；后来者需要的规则仍由 Agent 主动发布到 IOA，fork 历史不会自动成为共享知识。
- 分析与动态验证任务使用 async 重叠执行。至少发生一次有业务依赖的兄弟通信：接收者在实际 peer Inbox 中获得对方的新线索或请求证据，随后完成此前未能完成的验证。记录对应 HTTP/代码事实，不能用无意义的随机串交换替代。
- 独立复核可使用 sync，检查一个有界的问题或补丁；不强求每个阶段都保持并发。
- 已结束的子任务不继续等待消息。后续复测重新派发，引用前一任务与已有证据。等待期间的工具调用和模型成本计入预算；不新增持久子 Agent 或等待接口来掩盖现有能力。
- 避免多个修复者同时编辑同一文件：由协调者在 IOA 明确文件责任；第一轮最多一名代码写入者，其余角色执行只读分析和验证。

角色名和任务拆法可以由模型决定。测试通过公开 Session 事件、工具调用和实际行为确认角色与依赖，不靠模型给自己贴的标签判定。

## 两个必须处理的变化

**新增要求。** 首轮问题完成复现后，驱动通过公开用户输入发送一次真实的新要求：

> 已创建的导出也必须受当前权限约束。用户失去订单访问权限后，即使持有之前取得的下载链接，也不得继续下载；有权限用户的历史导出应仍然可用。请更新修复与验收范围。

这会要求跨越“创建任务时的权限”和“下载时的权限”重新推理。Agent 必须更新计划、实现权限撤销后的检查并验证正常历史导出，不得直接沿用旧结论。最终报告应标明这是新增要求，不伪称为基线阶段已验证的事实。

**中途换负责人。** 修复完成并启动最终验证后，驱动发送交接要求。原负责人需把当前修订、已证实问题、补丁状态、未完成验证、已知环境问题及原消息引用写入 IOA，再通过公开取消/关闭入口结束。接手者只收到业务目标、IOA 空间与工作目录位置，不收到前任对话或驱动整理的调查摘要。

变更触发使用可观察事件，例如带证据的复现记录、实际构建产物和开始执行的验证任务；不使用任意墙钟时刻。若一直没有达到触发条件，应报告阶段未完成，而不是驱动补全。

## 两个后端的交接语义

| 模式 | 交接操作 | 必须证明 |
| --- | --- | --- |
| 内存 IOA | 保留应用进程，关闭原主 Session；新建不继承历史的主 Session | IOA 历史仍可读；旧子任务取消或已完成；新负责人能识别并继续未完成事项 |
| 外部 IOA | 保留 IOA 服务与业务工作目录，关闭原应用进程；全新应用进程、Node 和 Session 接手 | 接手不依赖原 Agent 内存或本地对话记录；依据 IOA 历史与实际代码继续完成最终回归 |

根据当前生命周期，父执行退出会取消仍运行的子任务。本场景要求取消可见，接手者按需重新派发，不要求后台子任务跨父进程存活，也不要求自动恢复原执行栈。

已完成的验证不应无理由全部重做；取消、缺证据或修订发生变化的验证允许且应当重做。以任务阶段、源码修订、HTTP 证据和实际调用判断恢复是否合理，不能只看任务标题相同就认定重复。

主验收使用有界的正常关闭，检查 return/canceled 记录和资源释放。强杀进程恢复是后续独立变体：当前没有 outbox 或崩溃时的终态保证，不应把缺少 return 的任务误认为已完成。

## 一次有界的工具故障

在主场景加入一次可复现的导出轮询 503，后续请求恢复正常。依据首次特定阶段请求触发，记录故障时刻与 request ID，保持服务真实执行。

Agent 应将它识别为暂时不可用，进行有限重试或明确延期，不能直接报告漏洞、伪造成功或无限循环。若该 503 未被实际请求命中，故障恢复这一项为未覆盖，不能算通过。

首轮不同时叠加 IOA 断网、模型限流、多个 worker 崩溃和数据库损坏，以免失败后无法定位。业务变化、负责人交接、一次工具错误已形成足够长的依赖链；其余故障分别做可复现变体。

## IOA 中保留什么

自动 delegate / return 继续由 ext 负责。模型主动保存阶段计划、验证事实、决策及修正、需求变化和交接摘要；用现有消息内容与 Refs 关联，不新增工作流引擎、任务数据库、可靠消息层或专用通信工具。

每条关键证据至少能定位：审计批次、业务模块、适用源码修订、调用者角色、HTTP request ID 或测试产物、结论及所引用的 IOA 消息。稳定的 finding ID 可作为普通 JSON 字段沿用，不引入新的产品对象。

代码、测试和报告是工作产物，可以写入共享工作目录；Agent 之间的任务安排、发现和决策通过 IOA 交流。IOA 保存文件路径及内容摘要/哈希即可，不复制整个源码和全部命令输出。接手者可以重新检查代码与服务，不能读取前任模型对话或用隐藏的共享备注文件代替 IOA。

关键变更必须可追溯：旧消息仍保留，新结论引用并说明取代了哪条结论。只修改最终报告但没有留下修正依据，不能证明协作历史足以支持接手。

## 产物和判分

最终输出 `report.md`、简单的 `results.json`、实际代码 diff、新增回归测试和执行日志。`results.json` 包含问题状态、适用修订、复现/修复后证据、IOA 消息引用及未完成事项；格式用于验收，不注册成新协议。

| 维度 | 通过条件 |
| --- | --- |
| 业务结果 | 两处基线问题修复，权限撤销后旧导出不可下载；全部正常业务正例通过；不存在以停服代替修复 |
| 证据真实性 | 报告中的请求实际发生，身份/资源/状态/响应摘要一致；补丁后的结论来自补丁后的请求；隐藏用例使用新数据通过 |
| 长程一致性 | 新要求进入计划、实现和最终回归；旧结论被正确更新；未验证事项没有被标为完成 |
| 协作 | 真实模型自主派发任务；async 有执行重叠；fork 继承有证据；至少一次有效兄弟 peer Inbox 通信；派发/结果关联完整 |
| 恢复 | 新负责人没有继承前任对话，能够识别已完成、取消及待验证工作，并完成剩余阶段 |
| 故障处理 | 实际命中一次 503，有限重试后继续或正确报告阻塞；无无限循环、无伪造成功 |
| 工程交付 | 修改的是实际业务代码，新增测试可运行；独立验收针对交付修订重新构建、启动并通过；正常退出后资源释放 |

业务正确性由 HTTP 记录和独立可执行测试判定；协调质量由事件、消息、源码修订和调用顺序判定。自然语言建议由人工抽查，模型不能作为自己的唯一裁判。保留完整失败证据，不只保存成功报告。

记录总耗时、各阶段耗时、模型请求/token、HTTP 调用、峰值并发、纯等待调用、恢复后重复工作，以及是否人工提示下一步。若人必须补发调查事实、代改补丁或指出具体遗漏，记为人工救援；该轮不能算自主完成。

验收结果分别标记业务完成、协作、恢复和成本，不用单个总分掩盖某一项失败。一个场景成功说明可行，不说明可靠：首轮内存/外部各跑一次；之后预先确定三个种子复验，所有运行都计入成功率，不自动重跑到绿。

## 实施边界

1. 准备隔离业务项目和独立验收程序，先用人工已知正确的补丁校验正反例，确保判分有区分能力。
2. 复用现有真实进程、stdio、IOA 读取和 Provider 网关。放宽短场景写死的角色/指令序列，允许模型使用已有 bash/文件操作执行本地构建、测试、HTTP 检查和源码修改。保留工作目录、目标地址和总预算边界；不代写模型参数。
3. 用少量明确的场景函数触发需求变化、交接和一次 503，不建设通用故障编排平台。驱动可以启停环境、提供用户新要求、收集事件和判分，不能推进模型本应完成的业务步骤。
4. 支持将同一业务产物交给新 Session/进程；保留前任协议/模型日志供测试程序检查，但不暴露给接手者。IOA 服务不随原应用进程关闭。
5. 初始硬预算为每轮 60 分钟、200 次真实模型请求、累计 120,000 输出 tokens、600 次业务 HTTP 请求、最多三个同时运行的子任务；记录输入与缓存 token，并按实际模型价格评估成本。取消/关闭再给独立的有界清理期限。
6. 同步调整当前 harness 的 150 秒任务、4 分钟进程、固定两名 worker 和请求次数限制；保留全局上限，禁止以无限 turn 解决长任务。运行前确认配置和模型支持所需上下文长度。未观察到实际上下文压缩，就不宣称验证了压缩恢复能力。

测试驱动之外不预先改造产品架构。若现有等待、上下文、取消或证据读取机制导致失败，先记录具体复现和阻塞点，再决定最小修改。最终要回答的是：系统能否在有限预算内，把变化中的业务目标转化为正确、可复核、能由后来者接续的交付物。
