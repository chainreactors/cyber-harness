# 扩展装配与生命周期

[架构概览](../architecture.md) · 下一篇：[Agent 运行时](runtime.md)

一个应用要同时管理注册表、客户端、后台工作和会话。cyber-harness 把这些资源的拥有者表达为 Extension，由组合根决定顺序，再由 Set 统一加载和关闭。业务对象保留自己的接口，生命周期只在装配边界汇合。

## 从组合根到运行中的应用

组合根是一段显式的 Go 装配代码。它选择需要的扩展、传入配置与业务依赖，并按照依赖顺序调用 `extension.New(a, b, c)`。Set 不推导依赖图，也不通过包的导入副作用发现插件。

例如，基础组合先加载工具注册表，hello 扩展再贡献工具，最后宿主借用工具执行器。这样关闭时就可以倒序执行：先结束使用者，再移除贡献，最后关闭注册表。开发者不必为同一依赖再维护一份字符串 ID 或服务目录。

```mermaid
flowchart LR
    A[注册表与资源所有者] -->|Load| B[工具和知识贡献者]
    B -->|Load| C[会话与宿主消费者]
    C -.先关闭.-> B
    B -.再关闭.-> A
```

`harness.BaseExtensions` 按顺序提供 hooks、events、commands、toolset、skills、prompt、egress、文件与终端、tmux、app 和 provider。基础组合不包括 Agent 循环与 Session。参考发行版再加入领域能力、观察器、协议与宿主；具体组成以 [base](../../pkg/harness/base.go) 和 [aiscan profile](../../cmd/aiscan/profile.go) 为准。

## 贡献与借用

资源系统有两种关系。贡献用于把多个条目汇入一个领域所有者，例如工具注册表接受多个 `tool.Tool`。所有者用 `Define[T]` 定义贡献点，扩展用 `Add[T]` 提交条目。贡献点决定重复名称、快照、撤销和在途调用的规则。

借用用于共享一个已经存在的能力，例如会话借用 `tool.Executor`。所有者用 `Provide[T]` 发布能力，后续扩展用 `Use[T]` 借用。框架记录借用关系，使提供者不会在使用者仍然清理工作时提前消失。

| 关系 | 所有者 | 使用方 | 例子 |
| --- | --- | --- | --- |
| 多个条目汇入贡献点 | `Define[T]` | `Add[T]` | 注册模型工具 |
| 单个能力借给后续扩展 | `Provide[T]` | `Use[T]` | 借用工具执行接口 |

类型本身就是键，接口与实现类型不是同一个键。贡献者不能早于定义者，消费者不能借用自己或后面扩展提供的能力。固定的业务依赖也可以直接通过构造参数传入；不必把每个配置值都做成共享资源。

全部扩展加载成功后，资源注册表冻结，Set 才进入 Active。冻结后不能再定义新资源类型或建立新的借用；已有贡献点仍可按其领域规则增删条目。这允许运行期更新工具等内容，却不等同于动态重排整个扩展集合。

## 初始化与存活期

`scope.Init()` 携带本次加载的上下文，适合连接测试、资源初始化等需要启动超时的操作。`scope.Lifetime()` 是另一个由 Set 管理的上下文：它不继承 Load context 的取消，直到扩展关闭时才被取消。

因此，Load 成功后取消初始化 context，并不会自动关闭应用。宿主必须持有 Set 并明确调用 Close；扩展则把长期 goroutine、订阅和资源停止安排在自己的生命周期内。

部分 Load 失败时，Set 从失败的扩展开始逆序回滚，包含它已经注册的资源。Load 必须允许 Close 面对部分初始化的状态，不能假设每一个字段都已经建立。

## 关闭与重试

对于每个扩展，Set 先取消 Lifetime，再撤销它定义、贡献或发布的资源句柄，随后调用扩展自身的 `Close(ctx)`，最后释放它的借用。领域注册表负责停止接收新调用并排空该贡献的在途工作；扩展自身负责它启动的其他后台工作。

借用最后释放，是因为 Close 本身可能仍要调用依赖。例如，会话需要取消工具执行、等待结束并发布最终事件，事件流必须在这一过程结束后才能关闭。

普通关闭错误表示清理已经完成但发生了异常，Set 记录错误并继续关闭更早的扩展。若资源仍未回收，返回或包装 `ErrCloseIncomplete`；context 取消或超时也会被归入这一情况。Set 会停留在当前扩展，保留它和更早的依赖，供宿主使用新的关闭 context 重试。

## 配置声明先于运行装配

CLI flag、配置 section 和连接测试需要在解析配置前可见，因此使用单独的声明阶段。宿主先定义 `cli.Contribution`、`config.Section` 和 `config.Connection` 的贡献点，各功能包通过 `Declare` 加入自己的声明；随后冻结资源、Seal 领域注册表并解析配置，最后才构造运行扩展。

解析前贡献不会因此获得一个运行中的 Extension 生命周期。配置解析决定要安装哪些扩展、传入哪些值；运行装配决定这些资源如何开始工作和停止。把两个阶段分开，才能在连接模型和启动后台进程之前完成帮助、校验和配置选择。

## 领域边界

`core/resource` 负责类型关系和句柄生命周期，工具、命令、提示词等领域负责各自的冲突与执行规则。`pkg/exts` 连接业务资源与装配，`app.State` 不承担所有扩展的公共字段仓库。

关闭与并发行为的验证入口是 [Extension 测试](../../core/extension)、[Resource 测试](../../core/resource)和[领域注册表测试](../../core/registry)。扫描流水线另外拥有任务 DAG；它的路由关系不参与 Extension 的加载排序。
