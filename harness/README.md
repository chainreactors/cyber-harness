# Repository harness

`harness/` 承载仓库级架构约束与跨包系统场景。包内单元测试仍与实现放在一起；
跨边界场景通过公开 API 驱动系统，不为满足测试文件命名规则创建空实现文件。

运行：

```sh
go test -count=1 ./harness/...
# 或
make harness
```

当前包含：

| 场景 | 验证范围 |
| --- | --- |
| `architecture_test.go` | 依赖方向、构建约束、协议归属、测试跳过登记与仓库质量守卫 |
| `process_test.go` | 真实子进程中的 Host 与 AOP Stdio 编解码、多请求往返、EOF 退出和 stdout 协议完整性 |

子进程场景启动测试二进制中的 Host fixture，不需要模型、浏览器或外部服务。
它验证实际进程和传输边界，但尚未覆盖产品二进制的完整启动与业务流程。

Harness 是测试的驱动与验收机制，E2E 是覆盖范围；目录改名不会自动提高真实性。
后续系统场景应明确入口、受控本地依赖、预期产物和清理条件，验证输出、
持久化状态与资源回收。依赖真实模型或额外运行时的场景应显式选择运行，
并提供失败日志及必要产物。现有 Web E2E 继续维护自己的界面与服务断言。
